# Карта проекта

Общий стандарт лежит в `architecture.md` корня `freelanse`. Здесь только то, что
относится к этому проекту, и отступления от стандарта.

## Поток данных

```
project.json -> VideoProjectMapper -> VideoProject -> SceneTimeline -> FramePlan
             -> PillowFrameRenderer -> FrameImage -> FfmpegVideoEncoder -> mp4
```

Домен считает, что видно в каждом кадре. Он не знает ни про Pillow, ни про FFmpeg,
ни про файлы: всё внешнее спрятано за портами `FrameRenderer` и `VideoEncoder`.
Поэтому таймлайн проверяется обычными unit-тестами, без графики и без кодека.

## Почему кадр это сырые байты

`FrameImage.payload` содержит несжатые пиксели RGB в порядке строк, а не PNG.
Такой кадр отдаётся FFmpeg прямо в stdin как `-f rawvideo -pix_fmt rgb24`.
Сжимать каждый кадр в PNG, чтобы FFmpeg тут же его распаковал, значит платить
дважды за одно и то же. Диск при этом не трогается совсем: промежуточных файлов нет.

Контракт держится в двух местах, `PillowFrameRenderer` и `FfmpegVideoEncoder`,
и связан размером кадра из `CanvasSpec`. Разъедется он только вместе с разрешением,
а оно приходит обоим из одного объекта настроек.

## Слои

| Слой | Что внутри |
|---|---|
| domain | `VideoProject`, `Scene`, `SceneTimeline`, объекты-значения, порты, ошибки |
| application | `RenderVideoUseCase`, входные и выходные DTO, порт прогресса |
| adapters | маппер JSON, рендерер на Pillow, энкодер FFmpeg, команда CLI, отчёт о прогрессе |
| infrastructure | настройка логирования |
| entrypoints | чтение конфига, сборка зависимостей, разбор аргументов командной строки |

## Отступления от общего стандарта

1. **Контракт границы совмещён с маппером.** Отдельного типа `ProjectRequest` нет:
   внешний формат это JSON-документ, и `VideoProjectMapper` проверяет его поля сам,
   называя в ошибке номер сцены. Заводить ещё один промежуточный тип под один формат
   значило бы переносить те же поля лишний раз.
2. **Защита ветки `main` не включена.** Причина внешняя, см. `adr/0001-zashchita-vetki-main.md`.
